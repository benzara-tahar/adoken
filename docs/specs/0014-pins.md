## 1. Problem

"All day I bounce between the same few things: the PR I'm pushing to green, the two I'm reviewing, the story I'm on, and the pipeline that keeps breaking." In the web UI, each of those is a bookmark or a browser tab that is stale until reloaded, and each reload is a multi-second hub load. In adoken today every switch is a `⌘P` search (fast, but still typing and choosing), and nothing tells me that one of them changed until a notification fires or I open it. The things I touch most have no fixed place and no glanceable state.

## 2. Users and job to be done

- **Persona:** developer on Azure DevOps with a small working set (typically 3–10 items) that lives for days: own PRs in flight, reviews in progress, the current work item, the team's CI pipeline.
- **Job to be done:** "When I switch between the few things I'm working on, I want each of them one keystroke away with its current state visible, so I can switch without searching and notice changes without opening each one."
- **Smallest delightful slice:** `⌘D` pins what I'm looking at; it appears in the sidebar with a live status glyph and a change dot; `⌃1`…`⌃9` jump to it from anywhere. *(Amended 2026-10-02 by 0025 FR-2: no number jumps; pins open from the sidebar, rail or `⌘J`)*
- **Priority:** RICE 56 (Reach 70 · Impact 1 · Confidence 80%, dogfood request and GitKraken Launchpad precedent, `docs/competitive/gitkraken.md` §2.1 · Effort 1 week). Scheduled for v0.1 by the user on 2026-10-01 (Q-8).
- **Already assumed elsewhere:** 0002 FR-2 syncs "PRs I pinned" into the hot set and "runs of pipeline definitions I pin"; 0005 §9 offers pinning as the fix for mention coverage gaps; `crates/notify` has a "Build failed (pinned pipeline)" class. No spec owns pinning yet. This one does.

## 3. UX flow

### 3.1 Placement (sidebar group, Q-1)

Pins live in a **Pinned** group in the sidebar, after the sections. The sidebar is on screen in both of its modes, so pins are always visible:

- **Full view:** the expanded sidebar (232 px) shows one row per pin: glyph, title, headline status, change dot.
- **Compact view:** `⌘B` collapses the sidebar to the 56 px rail; each pin becomes one icon with its status tint, change dot and jump number. Hovering the rail's pins **peeks** the full group over the content without moving it.
- **Minimal view:** the group header folds the list into one summary line ("Pinned 5 · 2 changed · 1 failing").

### 3.2 Happy path

1. Reviewing PR !4821, press `⌘D` (or the pin toggle in the review header, or `⌘K › Pin`). The PR appears last in **Pinned** with its title and headline status ("Merge conflict").
2. Later, from anywhere (inbox, a diff, a comment composer), `⌃1` opens it. `⌃2` opens the second pin, and so on up to `⌃9`. *(Amended 2026-10-02 by 0025 FR-2: `⌃1`…`⌃9` are removed; open it from the sidebar or `⌘J`)*
3. While I work elsewhere, a teammate pushes to !4821: its row shows the change dot. Opening it clears the dot.
4. The PR merges. Its row shows "Completed" for the rest of the day and leaves the list 24 h after merging (FR-12).
5. `⌘J` opens the palette on the pins (`pin:` scope) for more than nine pins or a keyboard-only pick: type to filter, `↩` or `⌘1`…`⌘9` to open. *(Amended 2026-10-02 by 0025 FR-1: `⌘1`…`⌘9` are removed from the palette; `↩` opens)*

### 3.3 Alternate paths

- **Pin from anywhere:** `⌘D` pins the current subject: the selected palette result when the palette is open, else the focused list row or Today card, else the item open in the detail pane. A pipeline run pins its definition. A notification pins its subject. People, repos, projects and commands can't be pinned; `⌘D` on them shows "Only pull requests, work items and pipelines can be pinned".
- **Unpin:** `⌘D` on a pinned subject, the row's `⌘K › Unpin`, or the row's hover/focus unpin button. A toast "Unpinned !4821 · Undo" stays 5 s; Undo (or `⌘Z` outside text fields) restores it at its old position with its label.
- **Reorder:** drag a row, or `⌥⌘↑` / `⌥⌘↓` on a focused pin. Jump numbers follow the order. *(Amended 2026-10-02 by 0025 FR-2: pins have no jump numbers)*
- **Rename:** `⌘K › Rename pin…` sets a local label ("Payments CI"); empty resets to the ADO title.
- **Keyboard in the sidebar:** with the sidebar focused, `↑`/`↓` walk sections, then pins; `↩` opens; `⌫` unpins (with Undo).

### States

| State | Behavior |
| --- | --- |
| Empty | Expanded sidebar: the Pinned header and one hint row "Pin what you use daily · ⌘D". Rail: nothing. |
| Loading / first sync | Pins paint from the store with the rest of the sidebar (no extra wait). A pin whose item isn't stored yet (pinned from a pasted URL or direct id) shows its id with a skeleton title until the on-demand fetch lands (0003 FR-6). |
| Error | The item is gone or unreadable (404 / 403 on refresh): the row keeps its last title and shows "Not available" (reason in the tooltip) with Unpin. Other refresh errors follow sync's statusbar states (0002). |
| Offline / stale | Rows keep their last status; the stale rule of 0003 (> 3× the tier interval) dims the status glyph and says "Updated 18m ago" in the tooltip. Opening works offline. |
| Throttled by ADO | Pin refreshes wait with the other warm-tier requests; nothing pin-specific. |

## 4. Functional requirements

- **FR-1 Pinnable kinds.** Pull requests, work items, pipeline definitions. A run pins its definition; a notification, nudge or Today card pins its subject. Kinds whose scope is missing (0001: `vso.work`, `vso.build` are optional) can't be pinned; the pin action is disabled with the reason.
- **FR-2 Pin / unpin.** `⌘D` toggles the current subject (resolution order in §3.3). Also: a pin toggle in the headers of the PR review, work item detail and pipeline detail (tooltip "Pin ⌘D" / "Unpin ⌘D"); `⌘K` actions "Pin" / "Unpin" on any row; palette commands "Pin current item" and "Unpin…". Every user unpin shows the Undo toast (§3.3); Undo restores position and label.
- **FR-3 Order and cap.** New pins append. Reorder by drag and by `⌥⌘↑`/`⌥⌘↓`. At most **20** pins; a 21st is refused with "20 pins is the limit · unpin one first" and nothing changes.
- **FR-4 Sidebar group.** After the sections: header "Pinned" with the count, then one row per pin (kind glyph tinted by the headline status, title or label, headline status, change dot). The row whose item is on screen shows as selected. The group scrolls internally; sections and the bottom block stay fixed. The header toggles the group folded / unfolded; folded shows one summary line ("5 · 2 changed · 1 failing", or "5 · all quiet"). The fold state persists as `[sidebar] pinned_collapsed`. Pins ignore the project filter (`⌘O`): they are always shown.
- **FR-5 Rail.** With the sidebar collapsed, each pin is one icon: kind glyph with status tint, change dot, and its jump number for the first nine. Tooltip: "!4821 Retry idempotency keys · Merge conflict · ⌃1". A folded group is one pin icon whose badge counts pins with a change dot. *(Amended 2026-10-02 by 0025 FR-2: no jump numbers on rail icons, rows or tooltips)*
- **FR-6 Peek.** In rail mode, hover intent over the rail's pins (the submenu hover-intent and corridor from 0010 Z-7), or keyboard focus entering them, floats the expanded group beside the rail over the content. The content's layout doesn't change. Pointer leave (with the corridor grace), `Esc`, or opening a pin closes it. Reduce motion: appears and disappears without animation.
- **FR-7 Open.** Click, `↩` or `⌃n` opens the item's canonical view (design principle 5): PR → review (0004); work item → Work items with it selected, as for a palette target (0008 §3); definition → Pipelines runs filtered to that definition with its latest run selected (0008 §3). `⌘↩` / `⌘`-click opens it in the browser. Opening records the pin's last-opened time. *(Amended 2026-10-02 by 0025 FR-2: `⌃n` is removed)*
- **FR-8 Jump keys.** `⌃1`…`⌃9` open pins 1–9 from anywhere in the main window, including while a text field has focus (drafts persist per 0004); with no pin at *n* they do nothing. `⌘J` opens the palette in `pin:` scope listing pins in pin order; typing filters and `⌘1`…`⌘9` open the nth row (0003). Windows (v0.3): `Alt+1`…`Alt+9`, because `Ctrl+digit` are the section keys there. All bindings are overridable in `keymap.toml`. *(Amended 2026-10-02 by 0025 FR-1, FR-2: `⌃1`…`⌃9` (Windows `Alt+1`…`Alt+9`) and the "Jump to pin N" commands are removed, and `⌘1`…`⌘9` no longer open palette rows; `⌘J` and `pin:` stay)*
- **FR-9 Headline status.** One signal per pin, from the same store data as the kind's list row (0004 §3.1 PR rows, 0008 rows). First match wins:
  - **PR:** Completed / Abandoned → Merge conflict → CI failing → Changes requested (a reviewer voted Reject or Wait for author) → CI running → Approved (≥ 1 approval, no Reject or Wait) → Draft → Active.
  - **Work item:** its state name, tinted by state category (Completed / Removed, Resolved, In progress, Proposed).
  - **Pipeline definition:** its latest run: Running (with elapsed time) → Failed / Partially succeeded / Canceled / Succeeded; "No runs" when none is within retention.
- **FR-10 Change dot.** PR or work item: lit when a 0002 FR-11 event for the subject with `self_caused = false` arrives after the pin was last opened. Definition: lit when the latest completed run's result differs from the result shown when it was last opened (red → green or green → red), so a busy CI pipeline doesn't blink on every run. Opening the pin clears the dot.
- **FR-11 Freshness.** Pins are kept at hot/warm cadence regardless of project selection (§5): pinned PRs are in the 0002 hot set and first in its overflow order; pinned PRs outside synced projects are also refreshed by id each warm pass; pinned work items join the full work-item set (warm tier); pinned definitions' latest runs are fetched per project each warm pass. All requests go through the rate governor at normal priority.
- **FR-12 Auto-unpin.** A PR that completes or is abandoned, or a work item that reaches the Completed or Removed category, leaves the pins 24 h after it closed. Reopened within 24 h, it stays. Definitions never auto-unpin. Auto-unpin is silent (the item stays in palette recents). `[pins] auto_unpin = false` keeps closed items until unpinned by hand.
- **FR-13 Not available.** A pinned item answering 404 / 403 on refresh keeps its last title and shows "Not available"; it is never removed automatically.
- **FR-14 Labels.** `⌘K › Rename pin…` sets a local label of at most 60 characters; empty resets to the ADO title. The tooltip always shows the real id and title. Labels are never written to ADO.
- **FR-15 Storage.** Pins (kind, subject key, position, label, pinned at, last opened at, last seen run result) are user-authored **local** state in the org's store (`docs/adr/0001-local-store.md`, local tables): preserved by migrations and by any cache rebuild, never sent anywhere. One org per install, one pin list.
- **FR-16 Notifications.** A failed run of a pinned definition that isn't mine raises P2 "Build failed (pinned pipeline)" (`BuildFailedOther` in `crates/notify`). Unpinning a definition stops syncing its runs and its notifications. Pinning a PR or work item adds no notification; the change dot is the signal (Q-5).
- **FR-17 Accessibility.** The group is a `Role::List`; each pin a `Role::ListItem` labeled with kind, id, title, status, change state and shortcut ("Pinned pull request 4821, Retry idempotency keys, merge conflict, changed since you opened it, Control 1"). Every pointer action (open, unpin, reorder, rename, peek) has a keyboard path (§3.3, FR-6, FR-8).
- **FR-18 Demo and gallery.** The demo store seeds four pins: a PR with a merge conflict and a change dot, an approved PR, an active work item, a failing definition. Gallery stories: expanded, folded, rail, peek, empty hint, 20 pins (scrolling), not available, stale; one snapshot per built-in theme (AGENTS.md).
- **FR-19 Amendments to other specs** (applied 2026-10-01):
  - 0002 FR-2: pinned work items join the full work-item set; pinned PRs outside synced projects are refreshed by id each warm pass; pinned PRs rank first in hot-set overflow.
  - 0003 §3 / `docs/design/command-palette.md` §4: empty query shows a **Pinned** group (pin order, max 9) before Recent; new scope `pin:` (opened by `⌘J`); `⌘D` in the palette pins the selected result.
  - 0005 FR-3 table: "`BuildCompleted` failed, pinned definition, not mine → P2".
  - 0009 FR-1: new `[pins]` table (`auto_unpin`); `[sidebar]` gains `pinned_collapsed`.
  - `docs/design/principles.md` §2 and `docs/design/command-palette.md` §7.2: the Pinned group; global keys `⌘D`, `⌃1`…`⌃9`, `⌘J`, `⌥⌘↑`/`⌥⌘↓`. *(Amended 2026-10-02 by 0025 FR-2: no `⌃1`…`⌃9`)*

## 5. ADO API surface and limits

| Purpose | Endpoint (api-version 7.1) | Scope | Cost / limit notes |
| --- | --- | --- | --- |
| Pinned PR threads, reviewers | Existing 0002 hot-set requests | `vso.code` | Reuses hot-set polling. Pins count toward the 150-PR cap and rank first in its overflow. |
| Pinned PR outside synced projects | `GET {org}/_apis/git/pullrequests/{id}` (project optional) | `vso.code` | 1 request per such pin per warm pass (≤ 20). |
| PR push attribution | `GET {org}/{project}/_apis/git/repositories/{repo}/pullRequests/{id}/iterations` | `vso.code` | Only after a source-head change; match the iteration to the new source commit before attributing a push. The PR creator is not treated as the pusher. |
| Pinned work items outside the full set | `POST {org}/_apis/wit/workitemsbatch` with `ids` (max 200) and `$expand: relations`, the same payload shape as the 0002 full-set fetch (Azure DevOps rejects `fields` together with `$expand`) | `vso.work` | 1 request per warm pass when any exist; `errorPolicy: omit` so one deleted item doesn't fail the batch (omitted → FR-13). |
| Unselected work-item project identity | `GET {org}/_apis/projects/{name}` | Existing project-read access | One request per unknown project name; cache as a project reference, without selecting it for sync. |
| Latest runs of pinned definitions | `GET {org}/{project}/_apis/build/builds?definitions={ids}&maxBuildsPerDefinition=1`, plus 0002 live-run GETs for in-progress runs | `vso.build` | One builds request per pinned project per warm pass. No `finishTimeDescending` ordering: it can prefer a finished run over a newer queued run. The mock checks a newer running run; the recorded real-org sample below contained only completed runs. |
| Definition omitted from the latest-runs response | `GET {org}/{project}/_apis/build/definitions/{id}` | `vso.build` | Distinguishes a valid definition with no retained runs from 403/404. Valid-empty clears obsolete cached runs; refusal keeps the last title as “Not available”. |

- **Rate limits:** warm traffic is one GET per PR outside ordinary list coverage, at most one work-item batch, and one latest-builds request per pinned project. Unknown work-item projects, omitted definitions and changed PR source heads add the metadata calls listed above. All use the existing governor; pinning never bypasses the 10 TSTU steady-state target / 50 TSTU hard cap. Endpoint costs vary: the older baseline's average is not a safe estimate for these calls.
- **Polling freshness:** at the default foreground cadence, hot-set PR threads refresh within 60 s; out-of-coverage PR metadata, work items and definitions refresh on the 2 min warm tier. Custom intervals, background mode, pause and throttling still apply (0002 FR-4, FR-8, FR-9).
- **PAT scopes:** `vso.code`, `vso.work`, `vso.build`: all already in both the Review and Read-only sets (0001 §5.2). No new scope, nothing high-privilege. Missing optional scopes disable that kind's pins (FR-1).

### Read-only real-org sample — 2026-10-01

`cargo run -p adoken-sync --example sync_probe -- --pins` used a throwaway store, GETs and a read-only work-item batch. Org/project paths and ids were sanitized; no PAT or payload text was recorded.

| Endpoint | Requests | Response bytes | Latency | Reported TSTU |
| --- | ---: | ---: | ---: | ---: |
| PR GET-by-id | 1 | 4,928 | 221 ms | 0.0158 |
| Latest builds for definitions | 1 | 6,237 | 137 ms | 0.0443 |
| PR iterations | 1 | 5,197 | 168 ms | 0.0000 |
| Work-item batch | 1 | 14,355 | 96 ms | 0.0081 |
| **Pin-refresh sample total** | **4** | **30,717** | | **0.0682** |
| Definition availability GET (separate sample) | 1 | 3,776 | 96 ms | 0.0102 |

Reported `0.0000` is not a zero-cost guarantee. The separate ordering-comparison request cost 0.0654 TSTU and is excluded from the pin-refresh total.

The limited builds query selected the newest sampled run, but it was **completed**; there were **zero queued/running newest runs**. A later retry was canceled at the Keychain prompt. AC-9's live ordering criterion is therefore **not passed**. The read-only retry command is `cargo run -p adoken-sync --example sync_probe -- --pins-only`; it requires Keychain authorization and an existing queued/running build, and never queues a build itself.

## 6. Acceptance criteria

- **AC-1 Toggle and Undo.** Given PR !4821 open in review, when `⌘D`, then Pinned lists it last with its title on the next frame. When `⌘D` again, it disappears and the Undo toast shows; Undo restores it at its old position with its label. (unit: pin list; story)
- **AC-2 Subject resolution.** `⌘D` pins: the palette's selected PR result; the focused PR, work item, definition and run rows (a run pins its definition); an inbox row's subject; a Today card's subject; the open detail. On a person, repo or command row it pins nothing and shows the hint. Without `vso.build`, the pipeline pin action is disabled with the reason. (unit: subject resolver)
- **AC-3 Persistence.** Pins, order, labels and fold state survive restart. A store migration that drops and rebuilds cache tables keeps every pin. (migration test)
- **AC-4 Jump keys.** Given 3 pins, `⌃2` opens the second pin's canonical view, also while the comment composer has focus (the draft is kept); `⌃5` does nothing. After moving pin 3 to the top with `⌥⌘↑`, `⌃1` opens it. (unit + scripted smoke run) *(Amended 2026-10-02 by 0025 FR-2, AC-2: superseded: `⌃1` opens nothing and no pin numbers show)*
- **AC-5 Palette.** `⌘J` opens the palette with the `pin:` chip and the pins in pin order; typing "ssO" keeps only "Fix SSO redirect"; `⌘1` opens it. With an empty query, `⌘P` shows the Pinned group before Recent. (unit: palette) *(Amended 2026-10-02 by 0025 FR-1: `↩` opens it; `⌘1` does nothing)*
- **AC-6 Headline status.** Given a pinned PR with a merge conflict and a failing CI run, the headline is "Merge conflict"; when the conflict clears, "CI failing"; when it completes, "Completed". A pinned definition with a running latest run shows "Running" and its elapsed time. (unit: status precedence table, every rule)
- **AC-7 Change dot.** Given a pinned PR last opened at T, a non-self-caused `PrCommentAdded` at T+1 lights the dot; my own vote (self-caused) doesn't; opening the pin clears it. A pinned definition with 5 green runs since last opened has no dot; a failed run lights it. (unit, injected clock)
- **AC-8 Auto-unpin.** Given `auto_unpin = true` and a pinned PR completed at T, it is listed at T+23h59m and gone at T+24h. A work item reopened at T+2h stays. With `auto_unpin = false` it stays at T+72h. A definition with no runs for 30 days stays. (unit, injected clock)
- **AC-9 Freshness and cost.** On the mock server: a pinned work item not assigned to or created by me appears in one `workitemsbatch` request per warm pass and its state change shows within one pass; a pinned PR in an unselected project gets one GET-by-id per warm pass; three pinned definitions in one project cost one builds request per pass; unpinning removes the id from the next pass. A read-only real-org run records in §5 the TSTU cost of each endpoint and which run `maxBuildsPerDefinition=1` returns while a newer run is still in progress. (mock server + one recorded real-org ledger)
- **AC-10 Cap.** With 20 pins, `⌘D` on a 21st item leaves the list unchanged and shows the limit message. (unit)
- **AC-11 Rail and peek.** Collapsed sidebar: each pin shows its glyph and, for the first nine, its number; the tooltip names id, title, status and shortcut. Hover intent over the pins opens the peek; the content pane's width is unchanged (layout assertion); `Esc` closes it; with reduce motion on, no animation frames run. Keyboard focus entering the rail's pins opens the peek too. (story + unit: layout)
- **AC-12 Fold.** Folding the group shows "5 · 2 changed · 1 failing" for the matching fixture and persists `pinned_collapsed = true`; in the rail a folded group is one icon with badge 2. (unit + story)
- **AC-13 Not available.** A pinned work item omitted by `workitemsbatch` (deleted) or a pinned PR answering 404 shows "Not available" with its last title and stays until unpinned. (mock server)
- **AC-14 Notifications.** A failed run (requested by someone else) of a pinned definition creates one P2 "Build failed (pinned pipeline)" notification; after unpinning, the next pass requests no runs for it and a later failure creates nothing. Pinning a PR creates no notification by itself. (mock server + notify unit)
- **AC-15 Labels stay local.** Renaming a pin to "Payments CI" shows the label in the row and the ADO title in the tooltip; the mock server log shows zero requests caused by the rename; an empty label restores the title. (unit + mock server)
- **AC-16 Project filter.** With the project filter set to a project that has none of the pinned items, every pin is still listed. (unit)
- **AC-17 Gallery.** Every FR-18 story exists with one snapshot per built-in theme. (snapshot test)

## 7. Performance budget

| Interaction | Budget | Measured how |
| --- | --- | --- |
| `⌘D` → sidebar shows the change | Next frame (< 16 ms); the store write runs off the UI thread | Frame recorder in a story + unit |
| `⌃n` / click → target view first paint | Same as opening that item from its list (0004, 0008), + ≤ 1 frame | Frame recorder, both paths on the same fixture |
| Sidebar frame with 20 pins | Layout only: status snapshot computed off the UI thread after each store commit (debounced, like Today), ≤ 5 ms for 20 pins; no store access on the UI thread | Bench in `crates/app` + frame recorder |
| Peek open | ≤ 1 frame after hover intent fires | Frame recorder |
| Cold start | Unchanged (< 500 ms to first frame); pins load in the existing store-open pass | Launch timer |

Global rules (AGENTS.md) always apply: frame < 16 ms, Cmd+P < 50 ms on 100k items, cold start < 500 ms. Regressions are bugs.

The indexed 20-pin snapshot benchmark over the full demo cache measured a mean of **149.9 µs** (`cargo bench -p adoken --bench pins --profile dev`). `pins_smoke` exercises real shell entities, pointer hover/click, keyboard dispatch, persisted writes, Undo, composer draft preservation, palette filtering and 20-pin scrolling; screenshots are written to `target/pins-smoke/`.

The final real-shell pin smoke recorded **11.95 ms p99** across **129 frames**.

## 8. Success signal (telemetry-free)

- **Local stat the user can see:** the `⌘J` palette footer reads "Opened from pins 41× this week" (counted locally, never sent).
- **Dogfood:** for a working week, the builder keeps 3+ pins and opens them from pins or `⌃n` more often than by `⌘P` search (local counter above vs palette opens); no browser tabs kept open for pinned items.
- **Public replies:** posts about pins mention a pipeline or a PR by use ("pinned our flaky nightly") rather than asking where to find things.

## 9. Risks

- **Sidebar clutter.** Pins compete with sections for height. Mitigations: cap 20, internal scroll, fold to one line, auto-unpin of closed items.
- **Rail icons look alike.** Five PR pins are five identical glyphs. Mitigations: jump numbers on the first nine, status tint, tooltips, peek. *(Amended 2026-10-02 by 0025 FR-2: no jump numbers)*
- **`⌃1`…`⌃9` taken by macOS.** If the user turned on Mission Control's "Switch to Desktop *n*" shortcuts, macOS takes `⌃digit` before adoken sees it. [INFERENCE: these shortcuts are off until enabled; not verified on macOS 27.] Mitigations: `⌘J` still works, keys are rebindable, and the cheat sheet shows the active binding. *(Amended 2026-10-02 by 0025 FR-2: moot: the keys are removed)*
- **Pinned pipelines notify, pinned PRs don't.** Users may expect either both or neither. Mitigation: the pin toggle's tooltip on definitions says "Pin · failures notify you (P2)"; the rule is in Settings › Notifications.
- **Duplication with Today.** My own PRs already have tracks on Today; pinning them repeats them in the sidebar. Accepted: pins are the user's choice and serve switching, Today serves the daily overview.

## 11. Out of scope

- Pinning repos, saved searches, people, wiki pages, branches, single runs: repos stay with the PR repo filter (0004 FR-13) and deferred 0011; saved searches stay `docs/ideas.md` #6.
- Titlebar chips and a bookmarks bar (Q-1).
- Dragging list rows into the Pinned group (reordering by drag is in); add later if dogfood asks.
- Automatic or frequency-ranked pins (Q-7).
- Time-boxed pins ("pin for today"): auto-unpin of closed items covers the common case.
- Mirroring pins to ADO favorites or "Follow": following a work item makes ADO send emails, the opposite of less noise.
- Syncing pins across machines: no adoken server in the data path (roadmap principles).
- Pins in a menu-bar extra: belongs to `docs/ideas.md` #7 (menu bar mini-inbox).
