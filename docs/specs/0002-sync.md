## 1. Problem

The ADO web UI refetches on every navigation, so "check my PRs" costs seconds per click, and nothing is searchable across PRs, work items, and pipelines at once. The only push channel ADO offers (service hooks) posts to public HTTPS endpoints, so a desktop app cannot be pushed to; every "real-time" client has to poll, and naive polling hits Azure DevOps' throughput limits and gets the user's requests delayed across *all* their tools.

## 2. Users and job to be done

- **Persona:** any adoken user; they never see sync directly, only its freshness.
- **JTBD:** "When I open adoken, I want everything relevant to me already there and at most a minute or two old, without my az/CI/browser sessions getting throttled because of it."
- **Smallest delightful slice:** hot data (my PRs, my reviews, my running builds, my mentions) visible within seconds of launch, then kept fresh by budgeted polling.

## 3. UX flow

Sync is invisible except for:
1. **Status pill** in the shell: `Synced 12s ago` · `Syncing…` · `Offline — last synced 3 min ago` · `Throttled by Azure DevOps — resuming in 40s` · `Sync paused · until 15:00` · `Token rejected`. Click opens the Activity drawer's Sync tab (spec 0016, amended 2026-10-01), with per-kind state and the `X-RateLimit-Resource` string when throttled.
2. **`Cmd+R`** refreshes hot + warm tiers now (coalesced; repeated presses within 10 s are no-ops with a subtle "just synced" hint), including kinds set to "Manual only" and while sync is paused (FR-4a).
3. **Settings › Sync** (spec 0009, FR-4a): how often each kind syncs, background behavior, pause, Sync now with the last sync per kind, and an estimate of the rate-limit share.
4. **First sync after onboarding** fills the inbox progressively: hot tier first, then warm, then cold backfill; the app is fully usable throughout.

### States

| State | Behavior |
| --- | --- |
| Empty (no projects selected) | Pill says "No projects"; link to Settings → Projects. |
| First sync | Rows appear as each fetcher lands; pill shows "Syncing (hot) 3/5". |
| Error (5xx, DNS) | Tier retries with exponential backoff + jitter (5 s → 5 min cap); last good data stays visible with stale timestamps. |
| Offline | Detected via reachability; all polling paused; resumes with a jittered catch-up on reconnect. |
| Throttled | See FR-8; pill shows countdown and resource string. |
| Unauthorized (401) | All tiers stop for that org; the quiet rejected state of 0001 FR-15 (statusbar "Token rejected" / "Token expired", one `TokenRejected` event; no banner) (amended 2026-10-01, owner notes; accepted 2026-10-01). |
| Asleep / app hidden | Background cadence (FR-4a: same, slower ×5 or paused); paused while the Mac sleeps. |
| Paused by the user | No scheduled passes until resumed or the hour ends (FR-4a); ⌘R still syncs once, writes and their re-reads and per-item refreshes (FR-16) still go out. The pill reads "Sync paused · until 15:00" or "Sync paused" (spec 0016 FR-9). |

## 4. Functional requirements

### Scope of sync ("my world")

- **FR-1 Entities.** Project, Repository, Identity (me + referenced people), PullRequest (+ reviewers & votes), PrThread/Comment (hot set only), WorkItem (full fields for "mine", title-index for the rest; for full items also the description's raw source and format, all relations in server order (`wi_link`), and `synced_ms` / `full_synced_ms` freshness stamps: spec 0015 FR-29, FR-32, FR-34), WorkItemComment (discussions of "mine" items: text, mentions, and the raw source and format, spec 0015 FR-3), BuildRun (+ stages from the build timeline), SyncCursor. Schema and storage per `docs/adr/0001-local-store.md`.
- **FR-2 What "mine" means.**
  - **PRs (list level):** all *active* PRs in selected projects; plus *completed/abandoned* PRs from the last 30 days where I am creator or reviewer; plus PRs I pinned (0014) outside the selected projects, refreshed one by one (`GET {org}/_apis/git/pullrequests/{id}`) each warm pass.
  - **PR hot set (threads fetched):** active PRs where I am creator or reviewer, PRs where I set auto-complete in adoken, PRs where I was mentioned in the last 14 days, PRs I opened in adoken in the last 7 days, PRs I pinned (0014). Cap 150; pinned PRs first in the overflow order, then by recency.
  - **Work items (full):** WIQL `[System.AssignedTo] = @Me OR [System.CreatedBy] = @Me` limited to non-closed states or changed in the last 30 days; plus items from `[System.Id] IN (@RecentMentions)` and `IN (@Follows)` if those macros work over REST (see Risks); plus work items I pinned (0014), fetched with one `POST {org}/_apis/wit/workitemsbatch` per warm pass (`errorPolicy: omit`) when the WIQL doesn't return them.
  - **Work items (title index):** every work item in selected projects, latest revision only, fields `System.Id, System.Title, System.WorkItemType, System.State, System.AssignedTo, System.ChangedDate, System.TeamProject` — powers 0003 search at 100k scale. Toggle "Index all work items for search" (default **on**). If the backfill cost measured in the week-3 spike is too high for a project, that project's index is limited to items changed in the last 12 months (Q-2).
  - **PR title index:** completed/abandoned PRs older than 30 days are kept as title-only rows (id, title, repo, author, closed date) for 0003 search, backfilled in the cold tier via `searchCriteria.status=completed|abandoned` paging — **only if** the week-3 spike shows the cost fits the cold-tier budget; otherwise closed PRs drop out after 30 days (0003 Q-2).
  - **Builds:** runs requested by me in the last 7 days; runs for the source branches of my active PRs; runs of pipeline definitions I pin (0014; latest run per pinned definition via `builds?definitions=…&maxBuildsPerDefinition=1`, one request per project per warm pass; unpinning stops it). Status updates for any run in progress. Stages come from each run's timeline: running runs every hot pass (4 per pass), finished runs once (8 per warm pass), and only while the rolling 5-minute cost stays under 2 TSTU (a timeline costs ~0.04 TSTU, ten times a list call). Older runs of mine load on request (palette "Pipelines: load older runs", 50 per project per request, newest first, no events).
  - **Mentions:** `@<my-id>` in PR comments of the hot set (ids compared case-insensitively; stored lowercase); mentions in work item discussions by comment scan of my full-sync work items: a discussion is fetched when the item's `System.CommentCount` changes or it becomes mine, mentions come from `data-vss-mention` anchors and the comment's `mentions[]`. `@RecentMentions` stays unused until verified on an org with mentions.
  - **Pinned metadata (0014 §5):** an unknown work-item project is resolved by name and cached as a project reference, not added to selected projects. A definition omitted by the latest-builds query gets a definition GET to distinguish valid “No runs” from 403/404. PR push attribution reads iterations only when the source head changes; the creator is not assumed to be the actor. These calls share the existing governor.
- **FR-3 Retention.** Completed/abandoned PRs and closed work items leave the full set 30 days after closing (title index keeps them for search). Builds older than 14 days are pruned.

### Scheduling

- **FR-4 Tiers.**

  | Tier | Contents | Foreground interval | Background interval |
  | --- | --- | --- | --- |
  | Hot | Hot-set PR threads + reviewers, my in-progress builds, "me"-mention scan | 60 s (in-progress builds I'm watching: 15 s) | 5 min |
  | Warm | Active PR lists per project, my work items delta (`ChangedDate > watermark`), my recent builds | 2 min | 10 min |
  | Cold | Title-index delta (reporting revisions continuation token), repos, projects, identities | 30 min | 60 min |

  "Foreground" = app window key or visible in the last 5 min. Intervals get ±10% jitter. The table is the default; Settings › Sync changes it per kind (FR-4a); the governor (FR-8, FR-9) always overrides the user's choice (Q-1).
- **FR-4a User cadence (user decision 2026-09-30, supersedes Q-1's single hot-interval knob).** Each tier is split into lanes with their own due times, so every user-facing kind keeps its own cadence; the tier stays the lane's governor priority (FR-7).

  | Settings row | Lanes (tier) | Default | Shortest |
  | --- | --- | --- | --- |
  | My pull requests (mine & waiting on me) | hot-set threads + file lists (hot) | 1 min | 30 s |
  | All active pull requests | active PR lists per project (warm) | 2 min | 1 min |
  | Work items | my work items delta + discussions (warm) | 2 min | 1 min |
  | Pipeline runs | my in-progress runs + stages (hot); finished runs + stages (warm, never under 2 min) | 1 min | 30 s |
  | Search index and projects (not adjustable) | structure + title index (cold) | 30 min | — |

  - Choices: 30 s, 1 min, 2 min, 5 min, 15 min, 30 min, Manual only (only ⌘R). The minimums keep any single choice inside the FR-9 steady budget: kinds that query every project per pass start at 1 min, kinds that touch only my PRs and runs at 30 s; values under a minimum clamp up to it and the UI explains why.
  - **In the background:** Same, Slower (every interval ×5 — FR-4's background column; the cold lane goes to 60 min) or Paused (nothing until adoken is in front again). Default Slower.
  - **Pause sync:** Off, for 1 hour, until resumed. Scheduled passes stop; ⌘R, a write's re-read (FR-15), completing re-reads and per-item refreshes (FR-16) still go out.
  - A pass runs the due lane plus the other lanes of its tier due within a tenth of their interval, so equal cadences stay one pass (the default is exactly FR-4's three passes); a lane can therefore start up to 20% early (jitter plus sharing). When "my PRs" is faster than 60 s, hot-set threads older than 80% of its interval are refetched so each pass refreshes them (FR-6).
  - Rate pressure still wins: `< 50%` remaining multiplies warm and cold lanes ×4; `≤ 20%` runs only hot lanes, at ×5 their foreground interval and never faster than 5 min; `Retry-After`, 429 backoff and the FR-9 budget hold every lane.
  - **Estimate:** TSTU per 5 min = Σ lanes (measured TSTU per pass, smoothed; before the first pass the §13 spike's 0.004–0.008) × passes per 5 min at the chosen cadence, capped at the 50 TSTU self-limit; shown as a share of Azure DevOps' 200 TSTU (`~3% of your Azure DevOps rate limit`), with the measured last-5-minutes cost beside it and a warning above the 10 TSTU target.
  - Persisted in `settings.toml [sync]` (spec 0009 FR-1) and applied to the running scheduler at once, without a restart; ⌘P has "Sync: Pause until resumed", "Sync: Pause for 1 hour", "Sync: Resume" and "Sync: Settings…".
- **FR-5 Sleep, wake, network.** No requests while the Mac sleeps or the network is unreachable. Reachability comes from `NWPathMonitor` (only an explicit "unsatisfied" path is offline) and sleep from `NSWorkspace` will-sleep / did-wake notifications; going offline shows `Offline` in the pill at once, without waiting for a failed request. On wake: hot immediately, warm after 10 s; on reconnect: hot within 0–5 s (jitter), warm after 10 s; cold on its next slot. Error backoff from the outage is reset.
- **FR-6 Change-driven fetching.** Per PR, threads are fetched only when list-level signals change (`lastMergeSourceCommit`, reviewer votes, status) *or* the hot interval elapses; thread fetches for unchanged PRs rotate so each hot-set PR is refreshed at least every 5 min in foreground. Work items fetch via WIQL delta then `workitemsbatch` (≤ 200 ids per call) for changed ids only.

### Rate governor (every request goes through it)

- **FR-7 Concurrency.** Max 4 in-flight requests per ADO host (`dev.azure.com`, `vssps.dev.azure.com`). Priority queue: user-initiated (e.g. opening a PR) > hot > warm > cold; first come, first served within a tier. Clarified (user decision 2026-09-30, measured: a first-come queue held a PR's file list and blobs behind queued sync requests, 694 ms instead of 261 ms to the first file at 80 ms RTT): a free slot goes to the highest-priority waiter; hot/warm/cold together hold at most 3 slots, so the 4th is always free for user-initiated requests; a waiter passed over 8 times while a slot was free for it goes next whatever its tier (no starvation). The budget (FR-9) and pauses (FR-8) apply to every tier alike.
- **FR-8 Headers.** Parse `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `X-RateLimit-Resource`, `X-RateLimit-Delay`, `X-RateLimit-Cost`.
  - `Retry-After` present → no request to that host until it elapses (user-initiated requests are queued, and the UI says so).
  - `Remaining/Limit < 50%` → multiply warm and cold intervals ×4, pause cold backfill.
  - `Remaining/Limit < 20%` → hot tier only, at background cadence; cold paused until `X-RateLimit-Reset`.
  - HTTP 429 (`TF400733`) → exponential backoff 30 s → 5 min cap with jitter; pill shows throttled.
- **FR-9 Budget.** Steady-state target **≤ 10 TSTU per 5 min** (Microsoft's "normal user spike" level) and hard self-limit 50 TSTU / 5 min (25% of the global limit, leaving headroom for the user's browser, az, git). Measured from `X-RateLimit-Cost` when present; when absent, estimate by request count (cap 300 requests / 5 min).
- **FR-10 Debug ledger (local only).** Superseded by spec 0016 FR-24 (amended 2026-10-01): the Activity drawer's Network › Totals view, no longer hidden behind a setting, keeps the per-tier last-hour request counts and summed `X-RateLimit-Cost` and adds per-endpoint and per-origin groups. Work item writes, comments and per-item refreshes (spec 0015) count as user-initiated. Never uploaded.

### Output: the event stream (contract for 0005 and 0006)

- **FR-11** After each fetch, sync diffs old vs new rows in one store transaction and emits typed `SyncEvent`s. Events are persisted (so notifications survive restarts) and deduplicated by `(kind, subject_id, dedupe_key)`.

  | Event kind | Subject | Emitted when | dedupe_key |
  | --- | --- | --- | --- |
  | `ReviewRequested` | PR | I appear in reviewers (was absent) | reviewer-set version |
  | `PrCommentAdded` | PR | New comment in a thread on a PR I created/review/commented on | comment id |
  | `PrThreadResolved` | PR | Thread I started changes to fixed/closed | thread id + status |
  | `MentionedInPr` | PR | Comment contains `@<my-id>` | comment id |
  | `MentionedInWorkItem` | WorkItem | New mention of me in discussion | comment id |
  | `PrVoteChanged` | PR | Any reviewer vote changes on my PR | reviewer id + vote |
  | `PrPushed` | PR | `lastMergeSourceCommit` changes on a PR I review, or on any PR where I set auto-complete in adoken (0004 FR-12) | commit id |
  | `PrStatusChanged` | PR | completed / abandoned / draft↔published on my or reviewed PR | status |
  | `PrMergeConflict` | PR | `mergeStatus` becomes `conflicts` on my PR | source commit |
  | `WorkItemAssigned` | WorkItem | Assigned to me (was not) | rev |
  | `WorkItemChanged` | WorkItem | State/title/priority change on a "mine" item, by someone else | rev |
  | `BuildCompleted` | Build | A run I requested / for my PR / pinned finishes (result: succeeded, partiallySucceeded, failed, canceled) | build id |
  | `TokenRejected` | Account | The main transport's first 401 of a rejection episode (0001 FR-15, Q-6), or once when the stored token lacks a scope a newer adoken added to 0001 §5.2. Replaces `TokenExpiring` (amended 2026-10-01, owner notes; accepted 2026-10-01) | episode (token `authorizationId`) |
  | `TokenReplaced` | Account | adoken replaced an `az` token silently before it expired (0001 FR-20) | new `authorizationId` |
  | `TokenReplaceFailed` | Account | Silent replacement still failing 2 days before `validTo` (0001 FR-20); once per token | token `authorizationId` |

- **FR-12 Self-suppression.** Events caused by me (actor = my identity id) are emitted with `self_caused = true`; consumers hide them by default.
- **FR-13 First sync is silent.** The initial backfill does not emit events for pre-existing state older than 24 h (avoids a 400-notification welcome).

### Writes

- **FR-14** User actions (vote, comment, resolve, complete; work item field, link and comment writes, spec 0015) are sent immediately, bypassing tier scheduling but not the governor; UI is optimistic; on failure the change reverts with an error toast naming the cause (403 → missing scope per 0001). Work item writes show the cause inline on the edited element instead (0015 FR-7).
- **FR-15** Server wins: after a write, the affected PR is re-fetched in the hot tier within 5 s. For work items, the PATCH response (with `$expand=relations`) is the re-read; a posted comment is followed by one item GET (spec 0015 FR-7, FR-25).
- **FR-16 Per-item refresh** (spec 0015 FR-30/FR-31). One work item's fields, relations and comment pages can be fetched on demand at user priority (Sync this work item, `⌘⇧R`, and the one-time fetch of a partly synced item). It is allowed while sync is paused and for items outside the selected projects, emits events like a sync pass, and stamps the item's freshness (FR-1).

### 5.2 ADO realities (applies to every spec)

- **No push to local apps.** Service hooks deliver to web endpoints (Web Hooks consumer POSTs to a URL you host); the `vso.hooks*` scopes are marked "no longer public". A desktop app behind NAT cannot receive them, and a relay server would mean hosting user data (against local-first). **Decision: polling only.** Freshness = tier interval.
- **Rate limits are per user, not per app.** 200 TSTU per sliding 5-minute window; one TSTU ≈ a typical user's load for five minutes; normal activity spikes to ≤ 10. Over the limit, requests are delayed (up to 30 s each) and then blocked with HTTP 429 `TF400733`; the user gets an email and a web banner. Throttling adoken throttles the user's browser, CLI and git too — so the budget in FR-9 is a product promise, not a tuning knob.
- **Headers are advisory before delay.** `X-RateLimit-Remaining` etc. arrive *before* delays start, so FR-8 can slow down proactively. `Retry-After` must be honored.
- **Query limits.** WIQL 20,000-item truncation (silent), 32,000-char query length, 30 s execution time. `workitemsbatch` max 200 ids. Iteration changes max 2,000 per page.
- **Per-PR fan-out is the cost driver.** There is no "threads changed since T across a project" endpoint, so hot-set size × interval is the main dial.
- **Mentions have no feed API.** There is no REST endpoint for "things that mentioned me" in PRs; we only see mentions in PRs whose threads we fetch (the hot set). Documented limitation.

## 6. Acceptance criteria

Harness: a recorded-fixture mock ADO server with latency injection and scripted headers; injected clock; store in a temp dir.

- **AC-1** Given a fresh store and a mock org with 20 projects, 500 active PRs, 30 hot-set PRs, 2,000 "mine" work items and 100k title-index items, the first inbox row is painted within 3 s and the hot tier completes within 10 s at 80 ms RTT.
- **AC-2** Given foreground state, over 30 simulated minutes with no server changes, the scheduler issues hot, warm, cold passes at 60 s / 2 min / 30 min (±10%) and no other requests.
- **AC-3** Given the mock returns `Retry-After: 30` on any response, no request reaches that host for 30 s (clock-based assertion), including user-initiated ones, which complete after the window.
- **AC-4** Given `X-RateLimit-Remaining: 40` and `X-RateLimit-Limit: 200` (20%), only hot-tier requests are issued until `X-RateLimit-Reset`, at background cadence.
- **AC-5** Given a 429 with `TF400733`, the next attempt is ≥ 30 s later, subsequent failures double to a 5 min cap, and the status pill shows "Throttled" with the `X-RateLimit-Resource` text.
- **AC-6** Over a simulated steady-state hour (foreground, 30 hot-set PRs, 20 projects), total requests ≤ 300 per any 5-minute window and summed mocked `X-RateLimit-Cost` ≤ 10 per window when each call costs the fixture's value.
- **AC-7** Given a new comment containing `@<my-id>` appears on a hot-set PR, exactly one `MentionedInPr` event is persisted within one hot interval (+5 s), and no duplicate after 10 further passes.
- **AC-8** Given my own vote change, the resulting `PrVoteChanged` event has `self_caused = true`.
- **AC-9** Given the first sync over pre-existing data, zero events are emitted for changes older than 24 h.
- **AC-10** Given the network goes unreachable, zero requests are attempted until reachability returns; then hot runs within 5 s.
- **AC-11** Given a 401 response, all tiers for the org stop and exactly one `Unauthorized` state is raised (no retry loop, verified over 5 simulated minutes).
- **AC-12** Given the title-index continuation token is persisted and the app restarts, the next cold pass resumes from that token (mock asserts the token param) rather than starting over.
- **AC-13** Given a vote write fails with 403, the optimistic UI reverts within one frame of the response and the toast names the missing scope `vso.code_write`.
- **AC-14** While a full cold backfill of 100k title-index items runs, UI frame time stays < 16 ms (frame recorder in the perf harness).
- **AC-15** No request or log line contains the PAT in clear text (log scan in CI).
- **AC-16** (FR-4a) Given my PRs every 2 min, all PRs every 5 min, work items manual only and pipelines every 30 s, over 20 simulated minutes each kind's requests are spaced by its own interval (≥ 80%, ≤ 110%), finished runs never under 2 min, and no work-item request goes out. (`crates/sync/tests/sync.rs`)
- **AC-17** (FR-4a) Given every kind set below its minimum, the kinds clamp to 30 s / 1 min and total requests stay ≤ 300 in any 5-minute window.
- **AC-18** (FR-4a) In the background, Slower gives FR-4's 5 min / 10 min, Same the foreground cadence, Paused no request until adoken is in front again (then the overdue passes run at once).
- **AC-19** (FR-4a) Given a 1-hour pause, no request goes out for the hour and the overdue passes run when it ends; paused until resumed, only ⌘R syncs (once, manual kinds included); resuming picks the schedule up at once.
- **AC-20** (FR-4a) The scheduler reports the last successful pass per kind and the measured TSTU per pass per lane; the estimate math (passes per 5 min × cost per pass, background ×5, manual lanes dropped, 50 TSTU cap) is unit-tested in `crates/sync/src/cadence.rs`.

## 8. Success signal (telemetry-free)

- Dogfood week: zero ADO "your requests are being delayed" emails for the builder while adoken runs all day next to normal work.
- Network › Totals (spec 0016 FR-24; formerly the local debug ledger, FR-10) shows ≤ 10 TSTU / 5 min average in foreground.
- Build-in-public: the "we poll without getting throttled" thread gets replies from people who hit TF400733 with other tools.

## 9. Risks

- **`@RecentMentions` / `@Follows` over REST.** Docs call them web-portal-only. If they fail, fall back to comment scans on "mine" items (smaller coverage). Spike in week 3.
- **Hot-set cost scales with review load.** A reviewer on 150 PRs costs 150 thread calls per pass; the rotation rule (FR-6) keeps foreground cost bounded, freshness degrades gracefully to ≤ 5 min.
- **TSTU cost of reporting revisions backfill is unknown.** Measure with `X-RateLimit-Cost` on a real 100k project before enabling by default; fallback: index only the last 12 months.
- **Mention format.** PR comments encode mentions as `@<identity-guid>` tokens (case varies by client; sync lowercases them). Work item discussions encode them as HTML anchors with `data-vss-mention` plus `mentions[]` (7.1-preview.4). Neither verified on real mention data yet (§13).

- **Q-2** Index all work items for search by default? **Resolved:** yes — all work items, latest revision, 7 fields, Settings toggle, 12-month fallback for projects where the backfill is too expensive (FR-2).
- **Q-3** Which PRs to sync at list level? **Resolved:** all active PRs in selected projects, list level only; threads only for the hot set (FR-2).
- **Q-4** Also track every failed run on `main`? **Resolved:** no for v0.1; pinning a pipeline definition covers it (FR-2).

## 13. Spike results — 2026-09-25 (builder's personal org, read-only)

`cargo run -p adoken-sync --example sync_probe [-- --shapes <dir>]`: one baseline pass (warm → hot → cold) into a temp store, then one steady-state warm + hot round, with a per-endpoint ledger. The org is small (1 project, 1 repo, 14 work items, 2 completed PRs from 2024, 1 build from 2024, no mentions anywhere), so this measures fixed per-pass cost, not a busy reviewer.

- **Baseline:** 13 requests, 54.6 KB, 0.070 TSTU, ~5 s wall (Warm 8 req / 0.065 TSTU, Hot 1 / 0.004, Cold 4 / 0.002). 14 work items, 1 org, 1 project, 1 repo, 17 search docs, 0 events.
- **Steady state:** Warm 5 req / 0.020 TSTU, Hot 1 req / 0.003 TSTU → foreground ≈ 18 requests and **≈ 0.07 TSTU per 5 min** (budget ≤ 10). Per-PR thread fan-out (the dominant cost) could not be measured: no active PRs.
- **Headers:** `X-RateLimit-Cost` (TSTU, e.g. `0.00381`) came on 9 of 13 baseline responses even far from the limit; `X-RateLimit-Limit/Remaining/Reset/Resource`, `Retry-After` and `X-RateLimit-Delay` never appeared.
- **`@RecentMentions` / `@Follows` over REST:** WIQL accepts both (HTTP 200, no error); both returned 0 items in an org with no mentions or follows, so whether they return the right items is **unverified**.
- **Reality vs docs (fixed, regression tests in `crates/sync/tests/real_shapes.rs`):** `connectionData` is preview-only (`7.1` → 400 `VssInvalidPreviewVersionException`; sync uses `7.1-preview`); the reporting revisions feed sends identities as `"Name <unique name>"` strings, not objects, and returns only the requested fields (so `System.IsDeleted` must be requested); `System.Description` is styled HTML (stored as plain text); WIQL and `requestedFor` match me by sign-in name (`authenticatedUser.properties.Account`).
- **Unverified (no data):** mention markup in PR comments (`@<guid>` casing) and in work item comments (`mentions[]` exists on 7.1-preview.4 comments, empty here); reviewer votes and thread status on real review threads; PR-triggered builds (`triggerInfo["pr.number"]`); in-progress builds; 429/`Retry-After` behaviour. Build timelines were recorded (`type` Stage/Phase/Job/Task/Checkpoint, a single `__default` stage for one-stage YAML, `order` can be `null`, records unordered); sync fetches them since §13.1.
